# N4 交付记录：失败分类、驱动退出码与阶段停止点（2026-09-13）

对应指导：`docs/yujin_jiuxu_next_stage_execution_guidance_20260913.md` 第 8、10 节（V10—V11）。

## 1. 问题与触发工件

### 1.1 失败分类读错了字段

冻结驱动 `yujin-jiuxu-v23/commands/60_run_g0.sh:198` 从 `block_cause` 里匹配大写错误词：

```
reason="$(... print(task.get("block_cause") or task.get("status") or ""))"
case "$reason" in
    *MODEL_RUNTIME_UNAVAILABLE*|*TIMEOUT*|*TRANSPORT*) retry_task ;;
    *UNCERTAIN*) stop ;;
    *) stop "deterministic failure" ;;
esac
```

`TaskSettlementService.settle_attempt`（`runtime_commands.py:655`）只在 `BLOCKED` 时写该字段：

```python
"block_cause": failure_class.value if settled_status is TaskStatus.BLOCKED and failure_class else task.block_cause
```

因此历史 v23 快照确实出现 `waiting_retry / block_cause=null`——真实分类是
**小写枚举 `provider_transient`**，写在 attempt 行里，驱动从未读过。
结果是可重试的瞬时失败被当成确定性失败直接停住。

### 1.2 退出码会假成功

同一脚本 `call()` 返回子命令状态、主循环 `break` 后继续执行成功的收尾命令，
于是整个脚本仍可能返回 0；`grep ... | tail -1` 也会吞掉管道前段的失败。

### 1.3 阶段停止点不完整

原脚本以"快照里没有 READY"作为边界，这不等价于"该阶段证据已产生"，
也不区分 G0/G1/G2/G3 各自需要的证据。

## 3. 关键实现点

### 3.1 分类只读规范来源

`classify_attempt` 的输入是最后一次**已结算** attempt 的 `failure_class`
和该任务的 effect ledger。`block_cause` 只用于在原因里报告"它存在但不是规范分类，
未被用于判定"。`RecoveryAction` 的取值直接对应指导第 8.1 节的处置表：

| 指导情形 | `RecoveryAction` |
|---|---|
| 已确认可重试的 provider transient 且无未结算发送 | `retry_under_policy` |
| 已发送且结果不确定，或旧请求仍为 REQUESTED | `reconcile_first` |
| completed 原始响应已落盘 | `replay_completed` |
| 配置/basis/权限漂移 | `stop_dependent_work` |
| 确定性 schema/审校/物化/冻结长度失败 | `repair_owning_module` |
| 预算切片耗尽但仍有实际进展 | `escalate_budget` |
| 无进展、反复审校同一问题 | `change_strategy` |
| 未知分类 | `undetermined`（明确报告，不伪装确定性，也不默认可重试） |

判定顺序把**未结算发送**放在最前，**已落盘响应**放在其次：
一次已经发出的调用其不确定性高于失败本身，而一个已经拿到的响应比任何重试都便宜。

`safe_to_retry` 要求 `retry_under_policy` 且 `retryable` 且既无未结算发送也无未决请求。

### 3.2 退出码真实

- `must()` 记录并返回每个子命令的失败；调用方必须处理（`|| break` / `|| return`）。
- 日志函数不再使用管道。
- 收尾（`stage_exit_satisfied`）在主循环之后、退出判定之前执行，其自身失败计入 `FAILURES`。
- `FAILURES > 0` → `exit 1`；阶段证据未证明 → `exit 1`；未知阶段 → `exit 64`。

### 3.3 阶段停止按证据

`runtime roots` 从**当前 canonical commit** 读 `RootManifest` 与 TextRoot/PlanRoot，
给出 `committed_chapters` 与 `committed_volumes`。门限：

| 阶段 | 卷门限 | 章节门限 |
|---|---|---|
| G0 | 8 | — |
| G1 | 8 | 2 |
| G2 | 8 | 5 |
| G3 | 8 | 20 |

阶段在启动时先核验一次：证据已在就直接退出 0，不为已完成的阶段再花切片。
"没有 READY 任务"不再被当作阶段通过。

### 3.4 冻结 v23 与新驱动

v23 脚本保持冻结作为证据，不再修改。新逻辑放在受版本管理的 `scripts/60_run_stage.sh`，
可从现有脚本提取最小必要实现，不再长期维护两份独立逻辑。
