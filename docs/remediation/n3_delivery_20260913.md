# N3 交付记录：修订范围、宿主合成来源证明与进展判断（2026-09-13）

对应指导：`docs/yujin_jiuxu_next_stage_execution_guidance_20260913.md` 第 7、10 节（V06—V09）。

## 1. 问题与触发工件

### 1.1 范围不完整

旧 `_compose_scoped_revision` 只做了一件事：点名条目取模型结果，其余取父候选。
它仍然允许：任意新增条目进入结果、被点名条目消失、advisory 扩大修改范围、
被点名条目内部任意变化。它把"点名条目集合"当成范围，而不是把**已核验阻断问题**
当成范围。

### 1.2 直接提交风险（指导第 7.2 节确认）

`planning_context_loop.py:2440` 持久化宿主合成后的 `proposal`，
但保存的 `PlannerExecutionResult` 仍是模型原始 `raw_proposal`。
`materializers.py:487` 要求 `execution.plan_proposal == proposal` 且只能有一个匹配执行结果。
宿主一旦真的恢复了模型误改的内容，两者就不同：**即使合成候选复审 ACCEPT，
也会在正式提交时报 "Plan candidate requires one matching Planner execution receipt"**。

### 1.3 进展身份不稳定

`_blocking_signature()` 使用 kind + 条目 + 自由文本。换措辞会被当成新问题，
同一个问题的部分修复又可能被当成"未变"而误停；来回振荡每圈都算新进展。

## 2. 源码提交与生产调用路径

新增责任文件：`src/novel_agent/domain/plan_composition.py`（单一实现，loop 与 materializer 共用）。

```
PlanningContextLoopService._run（plan_revision 分支）
  → revision_scope(plan_review)              # 只取已核验的阻断问题
  → compose_scoped_revision(parent, raw, scope)
      → validate_composed_proposal           # 条目唯一性/集合/coverage/unresolved/basis/mode
  → build_composition_proof(...)             # 父候选 + 原始执行 + 审校 + 范围 + 规则版本 + 摘要
  → 持久化：合成 proposal / 原始执行 / proof / 合成执行（带 proof 与 raw 引用）

PlanCandidateMaterializer._planner_execution
  → 直接匹配路径保留（composition_proof is None）
  → 合成候选：_verify_composition
      → revision_scope(review)               # 从审校重新推导范围
      → compose_scoped_revision(...)         # 重新计算
      → 与呈交候选精确比较
```

## 3. 关键实现点

### 3.1 范围由宿主执行

- 只有 `issue.blocking` 的问题产生范围；advisory 不授予任何写权限。
- `PlanRevisionTarget.operations` 区分 `modify` / `add` / `remove`：
  "修改第四卷某字段"不蕴含允许删除第四卷。
- `PlanRevisionTarget.field_paths` 为空表示整条目在范围内（宿主结构化问题如此），
  否则只允许被点名条目内的**具名 payload 键**与父候选不同，条目身份（item_id / kind /
  provenance / source_ids）始终取父候选。
- 未授权新增不进入结果；未授权删除被恢复；未授权条目的 payload 逐字取父候选。
- 结构缺陷（缺卷、重复条目）需要宿主问题明确点名才产生 add/remove，
  "结构修复被永久锁死"因此不成立。

### 3.2 来源证明最小且可重放

`PlanCompositionProof` **不携带文档**：父候选、原始执行和审校都是可达工件，
proof 只带它们的 `ArtifactRef`、范围、规则版本和合成结果的内容摘要。
验证因此是**重新推导**而不是与存档副本比较：

- 拒绝：缺失 proof、范围与审校不符、摘要不匹配、规则版本未知、候选不是合成结果、
  两个互相冲突的合成执行。
- 原始模型输出与真实 receipt 保持不变；合成结果获得自己的执行记录，
  不沿用旧 ID 暗示内容未变。
- 直接匹配路径完整保留（`test_a_direct_execution_still_wins_over_a_composed_one`）。

### 3.3 合成后整体校验

`validate_composed_proposal` 检查条目 ID 唯一、条目集合等于
`(父集合 - 授权删除) ∪ 授权新增`、非空、`mode`/`project_id`/`base_commit`/`coverage`/
`unresolved`/`strategy` 与父候选一致。只比较 items 会漏掉这些伴随提案的变化。

### 3.4 进展判断跨切片一致

- 身份 = 类型 + 受影响条目 + 字段路径 + 适用约束（`blocking_issue_identity`）。
- 实际值/未满足条件单独保存（`blocking_issue_details`）。
- 前沿（checkpoint 的 `plan_blocking_signature`）同时携带
  `finding:` / `detail:` / `attempted:` 三段：`attempted:` 记录本次 run 已经花掉修订的问题，
  因此**振荡**（A→B→A）在回到 A 时被识别为已尝试过，而不是新进展。
- 判定：全部关闭 / 集合缩小 / 出现未尝试过的问题 / 同一问题条件严格变窄 = 进展；
  同一问题原样复述、或回到已尝试的问题 = 无进展。
- 条件变窄按词元子集比较，因此"越过 350 和 401 两处边界"→"越过 350"算进展，
  而换一种说法不算。
- 身份与前沿存在既有 checkpoint 中，未新增平行计数账本。
